# OpenCode 1.18.31 local server read-only verification — 2026-09-23

Windows x64, Node 24.19.0, installed `opencode-ai` executable version `1.18.31`. `scripts/inspect-opencode-server.mjs` started a separate headless server bound to `127.0.0.1` in a temporary working directory, with a random in-memory Basic-auth password. It read `/global/health` and the server's own OpenAPI 3.1 `/doc`, then connected the middleware's `OpenCodeOwnedAdapter` read-only. Health/version and adapter connection succeeded; two sessions were observed as `readOnly=true`, `ownerId=null`. No session was created, attached or commanded. The owned server was stopped and temporary state removed.

The pinned live schema documents `POST /session` creation with optional title/model, `POST /session/{sessionID}/message` and `/prompt_async` with required structured `parts`, model `{providerID, modelID}`, optional `variant`, `POST /session/{sessionID}/abort`, `POST /session/{sessionID}/permissions/{permissionID}` with `once|always|reject`, `/config/providers` and `/global/event`. This corroborates why the prior Bearer/text-only/Codex-shaped fixture could not justify control. The [official OpenCode server documentation](https://opencode.ai/docs/server/) describes a multi-client server, but does not give this middleware exclusive ownership of an existing TUI session. Exact permission answer receipt, event correlation, idempotent send/recovery and a safe instance policy still require design and real execution evidence. The plugin remains observe-only; no model/effort or command support is advertised from these schema reads alone.

After the live check, the observer's trust boundary was tightened: health alone no longer sets connected. It requires a valid bounded session list; health/list/read JSON have size limits, list/read reject redirects, IDs and list cardinality are validated, a read must return the exact requested ID, and a later 401 revokes connected status. The real 1.18.31 observer was rerun successfully with these checks. Focused adapter tests passed 6/6, including redirected/oversized/duplicate session lists, redirected/mismatched/expired reads and unsupported version rejection. Private standalone harness export v8 was copied outside both source repositories, clean-installed, built and tested 7/7 with zero npm audit vulnerabilities. These are observation-security results, not control acceptance.

`scripts/verify-opencode-isolation.mjs` then ran a separate opt-in OpenCode 1.18.31 server using temporary XDG data/config/cache/state directories and random internal Basic auth. Its initial session list was empty, unlike the two sessions seen by the earlier non-isolated server. It created one new verification session, confirmed its ID by list and read, and called abort on that ID. The script removed the temporary storage and stopped the process. The same script is included in v8's standalone `scripts/` and passed again from the copied export. It sent no model command, changed no existing session, and proved no permission or completion semantics. `docs/middleware/OPENCODE_OWNERSHIP.md` records the resulting owned-instance policy and the remaining L3–L5 checks; the adapter still advertises observation only.

The observer previously treated any syntactically valid health version as connected, although only 1.18.31 had been checked. It now rejects other versions with `unsupported_version` before the session-list handshake. Focused adapter tests passed 6/6, including a 1.18.32 rejection fixture; a fresh installed 1.18.31 read-only check connected and listed two existing sessions without commands. This is a conservative compatibility bound, not evidence for model control.
