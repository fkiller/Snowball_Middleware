# OpenCode control boundary — implementation checkpoint (2026-09-24)

This is the L3→L5 implementation design for MW.03.02.01.02, not a claim that control has shipped. The local Web UI remains noAuth/no PIN on loopback. An internal random Basic secret can protect the **middleware-owned OpenCode server connection** without becoming a user login ceremony. An arbitrary existing OpenCode TUI or server is observation-only.

## L3: trusted instance

An OpenCode control instance must be launched by the middleware from a user-selected canonical executable. Pin the reviewed executable hash and exact supported version before launch. Start `opencode serve` without a shell on `127.0.0.1` with an ephemeral port, no mDNS/CORS, a per-launch random Basic password held outside browser/API responses, and dedicated `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, and `XDG_STATE_HOME`. Explicitly decide whether and how provider credentials/config are imported; do not inherit arbitrary environment variables or silently copy another OpenCode home. Keep the owned process handle and storage identity. If it exits, the owner is lost even if another process later binds the port. Never treat a reachable external URL, a matching PID alone, or health alone as proof of ownership.

The production launcher in `apps/supervisor/opencode-owned.mjs` now pins the canonical executable and SHA-256, starts the checked 1.18.31 server without a shell, uses private HOME/XDG/APPDATA directories and an ambient-environment allowlist, verifies its loopback announcement and authenticated health, and requires anonymous 401 before giving an observe-only adapter to the core. The Windows verification listed zero pre-existing sessions in isolated storage, created one new verification session, returned the same ID from list/read, and accepted abort. A non-isolated server previously exposed two existing sessions, illustrating why process ownership alone is insufficient. No provider credentials are imported into the production launcher; a reviewed credential-import policy remains to be designed.

## L4: operation and session scope

Only a session created through this instance's `POST /session` can become controllable. Persist a write-ahead creation request receipt before the call; if the response is lost, mark identity unknown and do not retry automatically. A session discovered in `GET /session` starts read-only even inside isolated storage. A restart restores saved session metadata read-only/null-owner; re-acquisition requires re-launching the same reviewed storage/executable and explicit user selection after native ID inspection. Never transfer owner rights from a session title, project path, HTTP 200, or a bare server event.

For a new owned session, verify `/config/providers` and the selected provider/model against the live catalog. Send only the 1.18.31 structured `parts` body to `POST /session/{sessionID}/message` or `/prompt_async`, with `{providerID,modelID}` and an explicitly supported optional `variant`. Do not map Codex effort strings to OpenCode variants without provider evidence. A command is sent only to the exact plugin instance/session/owner recorded in the journal; another instance's event or permission request cannot satisfy it. Check the current session identity again before dispatch. Expose capabilities in the manifest only after the corresponding real-server tests pass.

## L5: outcome evidence and recovery

Normalize the real `/global/event` SSE schema with bounded frames and session/message/part correlation, including reconnect gaps. An HTTP response proves at most acceptance of the request body; completion requires matched native events or exact session message readback. After a transport failure or ambiguous response, report `unknown`, never resend automatically. Abort targets only the owned session's active command and does not imply provider completion. Permission prompts must carry exact native permission ID and selected session; a `once|always|reject` response is not recorded as accepted until an exact native receipt or corroborated state is observed. If OpenCode offers no such proof, keep the answer unknown and require manual inspection. Server exit, credential change, storage mismatch, version/hash change, or event gap revokes owner/control while preserving read-only metadata.

The observe-only adapter now obtains model IDs from the live `/config/providers` catalog. It reports an empty effort list because Codex effort values do not apply to OpenCode. On 2026-09-24 a structured parts/model send with tools disabled was attempted only in a new temporary verification session. The installed free provider returned HTTP 403: `OpenCode's free tier can only be used from within OpenCode`. That response is a native rejection, not a successful command. Acceptance remains open: define reviewed provider credential import, test a permitted real model/variant send, correlated completion, abort, permission answer, unknown-send recovery, restart/reconnect and cross-instance denial on **new verification sessions only**; repeat the installed release checks on macOS. Until then, OpenCode is an observer and `harness.create`/`harness.execute` remain absent from its manifest.
