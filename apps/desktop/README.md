# Native tray development launcher

The current complete source installation is the [common installer](../../README.md#one-shot-install): it includes MK20 and M5Stack by default behind one tray/API, with no USB device required during PC setup. M5Stack firmware 0.4.0 discovers new PCs and pairs the device-selected PC over LAN. Installed `Register-M5Stack.ps1` / `.sh` launchers remain optional USB maintenance tools; they are not required for PC onboarding. Dated package records below describe earlier reference packages; they do not imply inclusion of the current complete installer. Current design and verification live in the [central architecture](https://github.com/fkiller/Snowball_Control/blob/main/docs/ARCHITECTURE.md).

Requires Node >=22.12 for development. Install dependencies, build, and download the pinned Electron binary explicitly:

```text
npm ci --ignore-scripts
npm run build
npm run install:desktop
npm run start:tray
```

Optional `--data-dir ABSOLUTE_PATH` selects private local state. Optional `--codex-control-config ABSOLUTE_JSON_PATH` uses the selected pinned configuration documented in `docs/middleware/CONTROL_REALITY.md`. Its executable, Codex home and working-directory paths must be canonical (resolved, without a launcher alias or junction), because the plugin verifies them again before launch. Normal Web access uses loopback without login/PIN. A provider may need its own login.

Without an external config, choose `Codex CLI 연결…` in the tray or the onboarding page. The page supplies no path. Native dialogs select the executable, existing Codex home and working directory; the app checks the canonical binary, exact supported version (`0.153.4`) and SHA-256 and shows all choices for review. Approval starts a new owned plugin instance without restarting the core. A private ACL-checked file restores that choice on the next run; observed existing tasks stay read-only until explicitly attached. The onboarding page can remove one connection or reset all saved connection references after a native confirmation dialog. It leaves the provider login and task history intact. A broken saved connection degrades the tray but does not block the local Web UI; reset can repair corrupt JSON if the file ACL is still private. Interactive native dialogs have not yet been validated on the user's visible desktop.

There is no application front window. The native tray opens Supervisor/Settings in the default browser, pauses/resumes control, changes the real OS login item, shows diagnostics, and quits its own utility-process core. Single-instance ownership is scoped to the selected data directory. Plugin workers run separately from the native tray.

Settings persist in `settings.v1.json`. Autostart is re-read from the OS; a failed native change does not report success. `language` currently changes the native tray and OS notification text; Web translation remains Korean. Notifications summarize newly pending decisions or uncertain/failed commands without exposing task content. Muting does not replay old notifications on re-enable.

`npm run test:tray` creates isolated temporary state, uses no Codex account, shows no front window, exercises actual Windows tray creation plus loopback/no-PIN and pause/resume, then exits. It never changes OS autostart registration or shows attention notifications. Windows smoke passed on 2026-09-22. Actual login/startup, native notification delivery, sleep/wake, forced-crash descendant cleanup and macOS acceptance remain unverified.

`npm run package:desktop` creates a private, unsigned platform package from a reviewed application allowlist. `BUILD-INVENTORY.json` in `resources/app` records each copied application file's SHA-256. The current Windows x64 and macOS ARM64 CI packages have 96 matching inventory hashes and exactly 99 expected application files; both passed actual native tray, zero front windows, loopback no PIN and pause/resume smoke. The macOS ZIP passed the same smoke after extraction. The Windows installed executable passed this smoke after a clean per-user installation. On the owner's Windows PC, the installed runtime restored Codex control and OpenCode observation for two registered projects; an earlier real browser run created and resumed a separate owned verification task with two completed GPT-6-Astra/low responses. Existing tasks were not commanded. The new-task dialog defaults to the selected registered project. Initial Settings is closed under CSP and opens/closes on demand. The Windows observer distinguishes the MK20 QMK HID controller from the separate product CDC USB function and grants neither command control. Dead-owner private journal locks are recovered on startup after exact token and PID checks; a live owner is never displaced. A real CLI read-only dynamic enrollment/restoration/disconnect test passed from source without sending a command; the packaged picker itself was not interacted with. Signing, notarization, OS login lifecycle and production update remain separate gates.

The final package bundles Codex control and a read-only OpenCode observer. Development can select a pinned OpenCode 1.18.31 executable with `--opencode-observer-config ABSOLUTE_JSON_PATH` containing only `instanceId`, canonical `executable` and exact `sha256`; the launcher starts an isolated owned server with an internal random Basic secret. It does not import the user's OpenCode credentials or grant command control. The live current-user snapshot showed two ready projects, two connected harnesses, eight real OpenCode model IDs and one unsupported MK20 QMK USB candidate. Use the tray's Open Supervisor action after a restart because the loopback port is ephemeral. No existing user task was commanded in this observation.
